# ModelRoute V2 上架模型、密钥路由与渠道健康

## 业务边界

ModelRoute 只在请求进入核心服务前按当前 API 密钥的策略选择候选，并把公开模型名替换为渠道级内部模型别名。核心服务继续负责密钥鉴权、上游转发、Token 与缓存计费、预扣、失败退回、余额和最终消费日志。

平台不保存提示词或模型返回正文，也不重复计算实际用量费用。

## 多模型渠道与唯一模型价格

- 每条商户渠道保存一份上游类型、基础地址和密钥，并同步多个上游模型。
- 商户选择 OpenAI 兼容、Anthropic 或 Gemini，调用 `POST /api/merchant/channel-models/sync` 获取上游模型。
- 平台按规范化名称与管理员标准模型精确匹配，未收录模型不进入上架目录和路由。
- 管理员审核时可选择模型逐个发送 `hi`，再决定是否批准整个多模型渠道。
- 同一商户同一标准模型只有一个价格，倍率为 `0..50000` 基点；同一模型可由该商户的多条渠道共同承载。

模型上架时为每条同模型渠道生成独立内部别名。文本使用分层 Token 表达式，图片根据质量、尺寸和 `n` 生成按次表达式；全部同步成功后才整体激活。

管理员的“ModelRoute 官方”商户可以维护专用测试渠道；测试渠道地址和密钥属于已导入渠道数据，不作为普通商户新增渠道表单的默认值。新增渠道必须由提交人主动填写地址和密钥并完成同步、检测与审核。

模型市场和商户上架模型均返回 `channel_count`，只统计渠道状态为启用且健康状态为“健康”或“降级”的渠道。模型下所有渠道都进入冷却、恢复或停用后，市场接口直接隐藏该模型；至少有一条可用渠道时才会显示。

模型市场和商户上架模型接口同时返回 `call_count`、`token_usage` 和 `last_called_at`。三项数据按“商户 + 标准模型”关联的全部成功消费累计，调整倍率生成新价格版本后不会清零：调用次数只统计成功消费，Token 用量为输入与输出 Token 之和，最后调用取最近一次消费时间。模型市场和商户上架模型表都将调用次数、Token 用量和最后调用分别作为独立列，千以内不带单位，之后依次使用大写 `K/M/B` 紧凑单位，并以整数相对时间展示，不再显示价格数字。

## API 密钥与路由策略

路由策略必须绑定已创建的 New API API 密钥。平台只保存密钥 HMAC-SHA256 指纹，控制台将“API 密钥与路由”放在同一页，用户从密钥行设置策略。

默认策略为智能路由、稳定性优先、倍率区间 `0.00x..5.00x`。用户可选择：

- 智能路由：在倍率区间和健康状态合格的全部商户渠道中选择。
- 固定商户：只在选定商户中选择，再从该商户的合格同模型渠道中排序。
- 价格优先：先比较倍率，再比较健康、可用率和首字节 P95。
- 稳定性优先：先比较健康、可用率和首字节 P95，再比较倍率。

无候选时返回 OpenAI 兼容 `503/no_available_channel`。请求向客户端写出首字节前可切换下一候选；首字节写出后停止切换。

## 请求入口

- `POST /v1/chat/completions`
- `POST /v1/responses`
- `POST /v1/images/generations`

ModelRoute 不开放 `/v1/embeddings`。协议与入口不匹配时返回 `400/unsupported_model_protocol`。

## 真实调用健康与冷却

健康渠道不进行周期探活，`next_probe_at` 保持为空。真实调用更新成功率、首字节耗时和连续失败次数：

- `429`、`5xx` 和连接异常是临时故障。
- 连续 3 次临时故障后进入冷却，阶梯为 `1/5/15/30/60/120` 分钟。
- 冷却到期只执行一次主动探测；成功立即恢复健康并清零冷却等级，失败进入下一档。
- `401/402/403` 是硬故障，平台和 New API 渠道直接停用；商户更新渠道并重新审核后恢复。

Worker 只领取 `cooling/recovering` 且已到期的任务，不会扫描健康渠道。探测通过 New API 服务账号专用令牌执行，该令牌从结算同步中排除。

## 主要接口

商户：

- `POST /api/merchant/channel-models/sync`
- `GET|POST /api/merchant/channels`
- `POST /api/merchant/channels/{id}/models/sync`
- `POST /api/merchant/channels/{id}/status`
- `DELETE /api/merchant/channels/{id}`
- `DELETE /api/merchant/channel-reviews/{id}`
- `GET /api/merchant/offers`
- `PUT /api/merchant/offers/{model_id}`
- `POST /api/merchant/offers/{model_id}/status`
- `DELETE /api/merchant/offers/{model_id}`
- `GET /api/merchant/usage`

用户：

- `GET /api/routing-policies/{token_id}`
- `PUT /api/routing-policies/{token_id}`

管理员：

- `GET|POST /api/admin/models`
- `POST /api/admin/models/detect`

## 验证与回滚

本地全量测试覆盖多模型渠道、唯一报价、倍率边界、密钥策略、固定与智能路由、首字节切换边界、冷却递增、单次恢复探测、图片请求和内部别名隐藏。生产发布后执行 `deploy/scripts/verify-routing.sh`。

报价已经同步到 New API 时，整体回滚必须同时恢复同一时间点的平台库与 New API 库，避免别名、渠道映射和价格配置不一致。
