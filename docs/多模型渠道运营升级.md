# 多模型渠道与运营界面升级

## 渠道流程

商户在渠道弹窗选择 OpenAI、Anthropic、Gemini、DeepSeek、Qwen 或 Moonshot，填写一个上游地址和密钥后同步模型。平台通过核心服务读取上游模型，并按厂商和规范化名称匹配管理员模型目录。已匹配模型可创建正式绑定，未匹配模型只显示“平台未收录”。

提交渠道时服务端重新同步，不信任浏览器提交的模型清单。平台随后直接创建正式核心渠道；每个已匹配模型初始为“待检查”，商户必须在渠道模型弹窗中逐个检查。检查成功的模型变为“正常”并可上架，失败模型变为“错误”且不参与市场或路由。

渠道本身没有审核、启停或健康状态。商户可重新同步模型、逐模型检查和删除自己的渠道；管理员只查看渠道及逐模型状态，并可删除渠道。删除采用归档，历史调用关联继续保留。

## 接口

- `POST /api/merchant/channel-models/sync`：临时同步上游模型并返回匹配结果。
- `POST /api/merchant/channels`：服务端重新同步并直接创建正式多模型渠道。
- `POST /api/merchant/channels/{id}/models/sync`：刷新已创建渠道的上游模型。
- `POST /api/merchant/channels/{id}/models/{binding_id}/check`：商户检查单个渠道模型。
- `DELETE /api/merchant/channels/{id}`：商户归档自己的渠道。
- `GET /api/admin/channels`、`DELETE /api/admin/channels/{id}`：管理员查看或归档渠道。
- `GET /api/admin/channel-logs`：按平台渠道 ID 和商户用户 ID 读取最终消费日志。
- `GET /v1/models`：返回当前密钥已绑定且存在正常渠道模型的公开模型。

## 数据边界

`merchant_channels` 保存渠道容器；`merchant_channel_model_bindings` 保存上游型号、标准模型和独立健康状态；`channel_model_health_events` 保存真实请求、自动检查和手动检查产生的状态事件。报价和路由只读取 `healthy` 的模型绑定，因此同一渠道可为多个标准模型生成独立路由映射，且一个故障型号不会拖累同渠道其他型号。

MiniMax 不在厂商白名单、模型种子、图标、筛选和渠道选项中。
