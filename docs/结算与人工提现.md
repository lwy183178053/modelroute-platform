# ModelRoute 结算与人工提现

## 业务口径

- New API 最终消费与退款日志是结算事实来源，平台不重算输入、输出或缓存命中费用。
- 消费日志使用 New API 最终整数 `quota`。平台份额为 `quota / 10` 的整数商，剩余额度归商户，避免浮点账务。
- 商户归属由 `channel_id + 内部报价别名` 确定；浏览器和商户接口不会得到内部报价别名、New API 管理凭据或渠道密钥。
- 商户提现只冻结平台账本额度，不自动向外部账户打款。管理员审核后线下支付并登记凭证。

## 日志同步

Worker 每 10 秒运行一次结算周期，按消费类型 `2` 和退款类型 `6` 分页读取 New API 日志：

- 首次启动回看最近 24 小时。
- 后续使用 5 分钟重叠窗口，抵抗延迟写入和分页边界变化。
- 同步结束时间保留 5 秒安全延迟。
- `newapi_log_id` 唯一约束保证重叠窗口和并发周期不会重复结算。
- 只有两类日志的全部分页均处理成功，才推进同步水位；失败原因记录在同步状态表。
- 每轮先重试开放的对账项，报价映射恢复后可自动完成结算。

## 退款关联

退款优先使用 `task_id`，没有 `task_id` 时使用 `request_id` 关联原消费。多次部分退款通过退款分配表累计，最后一笔退款精确冲回原消费的商户与平台整数拆分。

异步任务可能只有退款日志写入 `task_id`。精确关联没有找到原消费时，仅在以下条件全部满足时使用保守回退：

- 商户、报价版本、用户、New API 渠道、模型别名相同。
- 原消费早于退款，且原消费日志本身没有 `task_id` 和 `request_id`。
- 过滤已完全退款记录后只剩一个候选。
- 该候选未退款额度足以覆盖本次退款。

没有候选、候选不唯一或额度不足时保持待对账，不猜测关联。管理员页面分别显示“原消费缺失”“原消费不唯一”和“原消费额度不足”。

## 商户账本

`merchant_ledger_entries` 只追加，不允许更新或删除。账本动作包括：

- `earning`：消费结算，增加可用余额。
- `refund`：退款冲正，减少可用余额并累计退款额度。
- `withdrawal_freeze`：提交提现，减少可用余额并增加冻结余额。
- `withdrawal_release`：驳回提现，释放冻结余额。
- `withdrawal_paid`：确认线下打款，扣减冻结余额并累计已提现额度。

退款发生在提现之后时，可用余额允许成为负数，用于保留商户欠款事实；冻结余额和累计字段保持非负约束。

## 提现状态

1. 商户提交金额、收款方式和收款账户，数据库行锁保证并发申请只冻结一次可用余额。
2. `pending` 可被管理员通过或驳回。
3. 通过后进入 `approved`，额度继续冻结。
4. `approved` 可确认线下打款进入 `paid`，或驳回进入 `rejected` 并释放冻结额度。
5. 重复审核、重复驳回和重复确认打款返回状态冲突。

收款账户使用平台主密钥加密保存。商户列表只返回掩码，管理员列表在服务端解密后返回明文；密文字段始终排除在 JSON 响应之外。所有提现和对账写操作要求同源请求并追加审计记录。

## 接口

商户接口：

- `GET /api/merchant/balance`
- `GET /api/merchant/ledger`
- `GET /api/merchant/withdrawals`
- `POST /api/merchant/withdrawals`

管理员接口：

- `GET /api/admin/withdrawals`
- `POST /api/admin/withdrawals/{id}/approve`
- `POST /api/admin/withdrawals/{id}/reject`
- `POST /api/admin/withdrawals/{id}/paid`
- `GET /api/admin/settlement-reconciliation`
- `POST /api/admin/settlement-reconciliation/{id}/ignore`

前端导航只是可见性控制，所有接口仍在服务端检查账号状态和普通用户、商户、管理员身份。
