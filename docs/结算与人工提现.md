# ModelRoute 自动入账与人工提现

## 业务口径

- 核心服务最终消费日志是调用事实来源，平台不重算输入、输出或缓存命中费用。
- 成功消费使用核心服务最终整数 `quota`，平台份额为 `quota / 10` 的整数商，剩余额度自动归商户，避免浮点账务。
- 已成功完成的调用不提供逐条退款、人工结算或人工对账功能；管理员补回用户额度通过用户额度调整完成。
- 失败调用由核心服务自动退回用户预扣额度。平台保留对应的内部冲正和幂等机制，避免把失败调用计入商户收入。
- 商户归属由 `channel_id + 内部报价别名` 确定；浏览器和商户接口不会得到内部报价别名、New API 管理凭据或渠道密钥。
- 商户可提现余额达到 `¥50` 后才开放申请，单次最低 `¥50` 且只接受人民币整数。
- 平台启动时读取核心 `quota_per_unit`；提现门槛、整数金额、税费和页面金额都使用该实际单位换算，业务口径保持 `¥1 = 页面余额 1.00`。
- 收款方式固定为支付宝。税率由管理员在“支付与充值”配置，范围为 `0.00%..100.00%`；例如税率为 `3.00%` 时，申请 `¥100` 会冻结并最终扣除 `¥100`，管理员实际打款 `¥97`。
- 每条提现申请锁定提交时的税率，管理员后续调整只影响新申请，不重新计算待审核或历史申请。
- 商户提现只冻结平台账本额度，不自动向外部账户打款。管理员审核后通过支付宝线下支付并登记流水与凭证。

## 日志同步

Worker 每 10 秒运行一次结算周期，按消费类型 `2` 和退款类型 `6` 分页读取 New API 日志：

- 首次启动回看最近 24 小时。
- 后续使用 5 分钟重叠窗口，抵抗延迟写入和分页边界变化。
- 同步结束时间保留 5 秒安全延迟。
- `newapi_log_id` 唯一约束保证重叠窗口和并发周期不会重复结算。
- 只有两类日志的全部分页均处理成功，才推进同步水位；失败原因记录在同步状态表。
- 每轮先重试开放的对账项，报价映射恢复后可自动完成结算。

## 内部失败冲正

退款优先使用 `task_id`，没有 `task_id` 时使用 `request_id` 关联原消费。多次部分退款通过退款分配表累计，最后一笔退款精确冲回原消费的商户与平台整数拆分。

异步任务可能只有退款日志写入 `task_id`。精确关联没有找到原消费时，仅在以下条件全部满足时使用保守回退：

- 商户、报价版本、用户、New API 渠道、模型别名相同。
- 原消费早于退款，且原消费日志本身没有 `task_id` 和 `request_id`。
- 过滤已完全退款记录后只剩一个候选。
- 该候选未退款额度足以覆盖本次退款。

没有候选、候选不唯一或额度不足时保留内部待处理状态，不猜测关联；该状态不开放产品页面或人工忽略接口。

## 商户账本

`merchant_ledger_entries` 只追加，不允许更新或删除。账本动作包括：

- `earning`：消费结算，增加可用余额。
- `refund`：退款冲正，减少可用余额并累计退款额度。
- `withdrawal_freeze`：提交提现，减少可用余额并增加冻结余额。
- `withdrawal_release`：驳回提现，释放冻结余额。
- `withdrawal_paid`：确认线下打款，扣减冻结余额并累计已提现额度。

退款发生在提现之后时，可用余额允许成为负数，用于保留商户欠款事实；冻结余额和累计字段保持非负约束。

## 提现状态

1. 商户提交整数申请金额和支付宝账户，数据库行锁保证并发申请只冻结一次完整申请金额。
2. `pending` 可被管理员通过或驳回。
3. 通过后进入 `approved`，额度继续冻结。
4. `approved` 可确认线下打款进入 `paid`，或驳回进入 `rejected` 并释放冻结额度。
5. 重复审核、重复驳回和重复确认打款返回状态冲突。

收款账户使用平台主密钥加密保存。商户列表只返回掩码，管理员列表在服务端解密后返回明文；密文字段始终排除在 JSON 响应之外。所有提现写操作都要求同源请求。

提现记录同时返回 `amount_quota`、`withdrawal_tax_bps`、`tax_quota` 和 `net_payout_quota`。税额按 `amount_quota * withdrawal_tax_bps / 10000` 的整数商计算；这些字段是按启动时读取的实际单位换算出的核心整数额度。驳回时释放完整申请金额，确认打款时从冻结余额扣除完整申请金额，税费和实际到账金额不参与浮点计算。

## 接口

商户接口：

- `GET /api/merchant/balance`
- `GET /api/merchant/usage`
- `GET /api/merchant/withdrawals`
- `POST /api/merchant/withdrawals`，请求只包含 `amount_quota` 和 `recipient_account`

管理员接口：

- `GET /api/admin/withdrawals`
- `POST /api/admin/withdrawals/{id}/approve`
- `POST /api/admin/withdrawals/{id}/reject`
- `POST /api/admin/withdrawals/{id}/paid`
- `GET /api/admin/channel-logs`

管理员提现列表支持状态筛选和 `20/50/200` 分页，进入页面和完成审核动作后重新统计待办数量。

前端导航只是可见性控制，所有接口仍在服务端检查账号状态和普通用户、商户、管理员身份。

- 本地真实 PostgreSQL 测试覆盖重叠日志幂等、并发提现冻结、`49/50/51` 元边界、整数校验、配置税率锁定、管理员即时可见、驳回释放、确认打款、部分退款和映射恢复重试。
- `deploy/scripts/verify-withdrawals.sh` 是只读生产验收脚本；它读取管理员提现列表和商户余额，不创建提现、不审核、不打款，也不访问已经下线的人工结算与对账接口。
- 生产发布前先运行 `deploy/scripts/backup.sh`，发布后核对第 5 份迁移、同步水位、Worker 日志和六个服务状态。
- 回滚代码时切换到上一不可变发布目录；涉及第 5 份迁移的完整回退使用发布前数据库备份和 `restore.sh`。
